# 熬鹰资本多平台监控系统：整体规划

日期：2026-10-30。状态：待用户评审的需求与执行基线；不构成生产发布批准。

## 1. 目标与边界

核心：跟踪熬鹰资本的观点、动态、开仓与仓位变化，支持用户及时跟随操作。
来源：Telegram 禁言群、聊天群（重点本人发言）、交易信号频道、消息通知群；X；Fomo；OKX。
手机：红米 K50，大陆网络、不连接 VPN 接收；每次真实仓位变化提醒，不按信号价值分级，不设计专属睡眠模式。
通知第一选择：自建 Gotify。现成 Android 客户端先验证；自研 App 是后续选项，不作为本期依赖。Gotify 不等于小米系统推送，也不保证持续响铃或必达。
隐私：业务消息不经第三方通知 SaaS；自有服务器仍可读取消息，Gotify 不提供本方案意义上的端到端加密。
后续：AI 根据原文、历史上下文与仓位变化生成交易对关注清单，区分事实与推断、保留出处。
本轮不包含自动下单、自动平仓、收益保证或完整看盘终端扩建。旧交易功能保留，不在本轮启用或扩展。

## 3. 架构与职责

来源适配器 → 原始事件持久化 → 标准化/身份识别/仓位变化 → 通知待发送队列 → Gotify → Android 客户端。
工作台读取持久化记录与健康状态；AI 异步消费事件，失败不阻塞采集和提醒。

- 原始记录：来源、账号、群/话题、外部事件 ID、源时间、采集时间、原文及编辑版本。
- 标准事件：观点、动态、开仓、加仓、减仓、平仓、仓位快照；未知字段保持未知，快照缺失不推断为平仓。
- 身份：按平台稳定账号标识映射熬鹰本人、助理和其他成员，名字只作显示。
- 去重：来源内按稳定 ID 与版本去重；跨平台先关联，只有足够证据才合并通知，防止把真实新操作误吞。
- 投递：保存事件与待发送任务保持事务一致；状态 pending/sending/sent/failed，超时恢复、有限退避、人工重试。sent 只代表 Gotify 接受，不代表手机收到或人已看到。
- 过期：补收消息标注原始时间与延迟；断线补发的响铃策略需评审，避免把旧信号当实时操作。
- 安全：HTTPS 正常验证、独立随机凭证、最小权限、日志脱敏、备份权限与保留期；不在仓库保存密码/令牌。
- 运维：采集、数据库、投递、Gotify、手机连接分别观察；外部探活才可发现整台服务器失联；欠费/续费检查列入运维清单。

## 4. 分阶段执行与关卡

### P0 基线盘点与方案确认
盘点服务器实际配置/数据库结构/现有推送记录、本地差异及相关测试；核实所有来源入口。
交付：保留/修复/替换清单、来源可获取能力表、发布与回滚清单。
验收：当前与目标架构可对照；未知项有记录；不把现有个人交易适配器误认为能读取博主私有订单。

### P1 通知可行性验证（最先执行的技术验证）
独立 Gotify 服务，优先轻量二进制与 systemd，绑定本机端口；HTTPS 入口、证书与域名方案明确后才开放手机访问。先发合成测试，不接生产交易内容。
K50 配置通知、声音、自启动及后台省电例外；分别测无 VPN 的 Wi-Fi/移动网络、锁屏、清后台、长时间待机、切网、断线恢复。
建议验收：至少 24 小时、100 条带序号测试，在线且网络正常时到达率 100%，延迟 P95≤5 秒；记录源端、Gotify接受、手机实际显示时间，手机时间人工或辅助记录。网络断开单列统计，补收顺序与数量一致。具体阈值评审后锁定，不承诺未来必达。
关卡：可靠性不通过，先定位网络/手机保活，不进入多平台扩建；收到但声音不足则单列接收端改造，不宣称 Gotify 已满足叫醒需求。

### P2 Telegram 可靠监控闭环
四话题逐一核对过滤和身份；实现待发送队列、恢复、幂等、故障可见性，接入已验证的 Gotify。
验收：四来源样本回放；开加减平各样本；编辑、重复、程序重启、发送超时、鉴权失败、数据库失败不静默丢失；存量数据库迁移前备份并验证恢复。
本地验证后提交具体部署差异，用户批准再上线；不上线整个尚未验收的新版交易功能。

### P3 多平台采集
每个平台按“入口核实→访问资格/接口→延迟与限频→历史回填→样本验证→接入”的顺序独立交付。
X：先本人发帖，回复/转推/引用范围待定。Fomo：先确认具体平台与公开账号/链上地址。OKX：先确认公开跟单或其他可访问入口；私有订单不可凭账号名字读取。
验收：每平台明确可见范围和检测延迟，断线重连与分页不漏；平台缺数据明确显示不可获取，不伪造完整仓位。

### P4 统一信息工作台
围绕熬鹰资本提供跨平台时间线、仓位与变更记录、来源筛选、原文回溯、投递状态和健康页面。复用现有 React 工作台，按实际使用收敛页面。
验收：每条变化能定位原始依据；失败与无数据呈现不同；手机查看链接大陆可达。

### P5 AI 研究辅助
先确定外部模型的数据披露边界；未确定不发送私人原文。异步生成标的、倾向、理由、条件、失效条件和证据链接。
验收：建立人工标注样本评估标的识别、引用忠实度、过期信息与幻觉；模型失败不影响监控通知；不直接触发交易。

## 5. 发布与验收纪律

每阶段均更新任务状态、证据、风险和下一步；未通过关卡不以“代码写完”算完成。
代码变更先保护现有未提交工作，局部改造，不启动第二个复用生产 session 的 Telegram 客户端。
按仓库约定执行相应测试、静态检查；涉及前端跑构建与渲染验证。环境不支持时明确记录，不谎报通过。
本地迭代→用户验收→明确批准 push→明确批准部署；服务器改配置、安装、重启亦须批准。禁止 kill -9。
部署前数据备份、变更清单、健康基线；失败恢复旧版本/配置，不删除生产数据库，数据库变更需可恢复方案。

## 6. 尚需确定的输入

1. HTTPS：用户是否持有域名；没有域名时评估可信 IP 证书或受控证书信任方案，不默认明文登录或关闭验证。
2. K50 当前系统版本；现成 Gotify 客户端是否满足声音强度，由 P1 验证。
3. 熬鹰 X/Fomo/OKX 实际入口和稳定身份标识。
4. Telegram 聊天群通知是否仅本人；助理名单；观点/动态提醒声音偏好。仓位变化每次提醒已确定。
5. 历史补发响铃、消息/媒体保留期、月预算、AI 数据披露边界。
