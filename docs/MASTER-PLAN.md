# 整体规划：自有服务端＋原生安卓 App

2026-10-30，按本轮用户明确需求整理。本文件替代此前 Gotify 路线，当前需求以本文件为准。

## 目标与边界

持续跟踪熬鹰资本在 Telegram 四话题、X、Fomo、OKX 的观点、动态与实际仓位变化，帮助用户及时自行跟随操作。
手机为红米 K50，大陆网络不连接VPN接收。每次真实仓位变化都提醒，不按交易价值分级、不设计专属睡眠模式。
App展示当前仓位、历史变化、跨平台动态与原文，后续展示AI关注清单。当前不实现自动下单/平仓，不扩建交易终端。

## 架构

来源适配器 → 原始记录与编辑版本 → 身份映射/标准事件/仓位差异 → 事务性待投递队列 → 自有HTTPS/WSS → 安卓App本地持久化与提醒 → 设备回执/人工确认。

服务器负责境外平台访问，手机不直接采集Telegram。App为客户端，非公网服务器。
原生安卓技术候选为Kotlin，先做最小原型验证；数据库、后台服务及网络库的具体选择在接口设计时记录决策。
网页管理端后置，新项目不复制旧工作台。

## 数据与消息语义

- 原始记录保存来源、稳定账号ID、外部消息ID、版本、源时间、采集时间、原文和编辑历史。
- 事件区分观点、动态、开仓、加仓、减仓、平仓及快照，未知字段保持未知；快照缺失不推断平仓。
- Telegram同时监听新消息与编辑，并定期核对；同一条动态消息的多次仓位操作分别形成变化记录。
- 价格、浮盈、更新时间变化只更新展示，不当作仓位操作。
- 来源内按ID/版本去重；跨平台先关联，仅足够证据时合并提醒，避免误吞不同操作。
- 事件与待投递任务事务一致，有限退避、失败可见、重启恢复；App确认本地保存后才回传接收回执。
- 排队/发出/设备收到/用户已知晓分开记录；确认只表示看到，不表示已交易。
- 历史补收标注延迟；过期消息响铃策略待确定，不默认按实时信号处理。

## 隐私与运行边界

不经第三方通知SaaS；TLS正常校验，设备独立授权、可撤销，日志脱敏，备份和密钥分开管理。
端到端加密、存储加密和锁屏摘要策略需设计并验证，不因自建就宣称已实现。服务器需要读取来源内容。
后台连接采用用户可见常驻服务；K50自启动、省电例外及通知权限须实测。不能承诺被系统强行停止、关机或断网后仍可即时提醒。
AI异步且后置，未确定披露边界前不向外部模型发送私人原文。

## 路线与阶段关卡

| 阶段 | 交付 | 完成条件 |
|---|---|---|
| P0 基线与协议 | 来源能力表、事件/设备/回执协议、隐私与存储方案 | 入口和未知项明确，协议可测试 |
| P1 最小手机闭环 | 合成事件服务＋K50接收原型、响铃与停止、重连补收 | 通过P1-VALIDATION.md；失败先定位，不扩建 |
| P2 Telegram | 四话题采集、编辑和周期核对、仓位差异、持久化投递 | 开加减平回放与失败恢复通过；不复用旧会话 |
| P3 多平台 | X、Fomo、OKX逐项接入与来源关联 | 可见范围/检测延迟/限频/回填经验证，不假设可读私有订单 |
| P4 完整App | 仓位、动态、变化记录、详情、连接与提醒设置 | 全部记录可追溯，失败不显示成无数据 |
| P5 AI | 标的、倾向、理由、触发/失效条件、原文依据 | 人工样本评估引用与标的准确性，失败不阻塞通知 |

每阶段先细化任务及验证再实现，完成后记录证据。P1用合成事件；P2前无真实信号监控。

## 发布与运维

用户已授权独立新仓库上传及独立服务器实测，不重复套用旧项目发布限制；不扩大到交易或私人数据外传。
独立服务、账号、数据、端口；不将凭证入Git。变更前准备回滚、涉及数据时验证备份恢复。禁止kill -9。
分别观察采集、数据库、队列、连接和设备状态；整机故障需要独立探活，欠费和证书续期纳入检查。
当前使用可信IP证书与每天两次续期检查；业务入口暂时返回404。HTTPS是通用设施，不是Gotify依赖。
