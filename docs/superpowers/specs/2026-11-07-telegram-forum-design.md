# 熬鹰书友会四分区采集设计

## 范围与批准
仅监控「熬鹰书友会」（chat_id=-1002568478710），排除「熬鹰WEB3」和账号其他会话。用户先确认四区全部采集与筛选，随后要求修改设计：按四区实际用途和优先级重新规划，而不是四区等权处理。本文当前为修订草案，尚未批准实施；采集、通知和解析规则均为建议，不代表已部署。
用户给出的业务优先级：交易信号推送最高；禁言群与聊天群同样重要，其中聊天群重点关注熬鹰本人；消息通知低优先级。只读监控，不执行交易。

## 方案比较
1. 只按群采集：改动少，但四区混流，不满足分类需求。
2. 只采交易信号区：噪声少，但会遗漏其他区的重要发言，不符合已确认范围。
3. 四区分别回补与跟踪、统一消息表展示（采用）：保留群和消息的既有身份，增加话题维度，避免高流量聊天区挤占其他区的首次回补。

## 存储与归属
新增话题实体，关联 TelegramDialog，记录 topic_id、title、enabled、last_message_id、last_synced_at。唯一约束为 (dialog_id, topic_id)。TelegramMessage 增加可空 topic_id；既有 (dialog_id, message_id) 唯一约束不变，编辑历史和删除仍按原消息身份关联。
从 Telethon reply header 的论坛根话题字段识别消息归属，不能将普通 reply_to_msg_id 无条件当作话题 ID。General、话题根服务消息、嵌套回复分别通过真实元数据与单元测试验证；无法可靠判定的历史消息保留为未分类，不猜测归属、不删除。
现有数据库保留账户和登录数据。上线前备份数据库，执行可重复运行的显式升级，不能仅依赖 create_all 给旧表加列。完整 Alembic 数据地基仍留在 I2.2，不在这里扩展。

## 采集与补洞
首次每区回补最近 200 条，按由旧到新落库；后续使用各区独立游标。General 的分页方式需按当前 Telethon API 实测，不默认 reply_to=1 就可正确返回 General。分页、过滤不得让其他区消息消耗该区 200 条额度。
实时事件只接收目标群且属于启用话题的消息；未知话题不自动扩大监控范围。关注和同步状态按区展示。删除事件缺少可靠 chat_id 时仍沿用保守策略，不跨群匹配。
启动前核对数据库中 enabled 的群，仅启用目标群；不删除其他账户数据。一个 session 同时只由一个采集进程使用；探测脚本结束后再启动服务，避免 SQLite session 锁冲突。

## API 与界面
沿用现有 Telegram API、React 时间线和数据源页面。返回话题 ID、名称和同步状态；消息接口增加 topic_id 筛选参数。时间线增加分区标签与筛选，保留类型、时间、关键词、编辑历史和删除标记。未分类旧消息明确标识，不误标为聊天群。默认显示已确认四区的消息。

## 错误和验证
单区同步失败不得错误推进该区游标；记录失败状态，其他区可继续。重复同步不得新增重复消息或编辑版本。未授权 session、网络超时、无权限均显示具体状态，不打印凭证。
先编写并运行失败测试，再实现：话题归属（General/根消息/嵌套回复/未知）、每区最近 200 条及独立游标、重复同步、旧库无损升级、API 分区筛选、前端标签与筛选。回归现有后端测试、TypeScript、Web 测试和构建；每项区分实测通过与环境未验证。
真实验收仅查询目标群：核对四区标题、每区落库计数与最新时间、API 分区返回和页面展示；不在交付报告展示私人消息原文。实时新增或编辑事件未实际观察到时，明确写待验证，不能以历史回补冒充实时验证。

## 修订后的业务路由（建议，待确认）
原文采集层与重要信息层分开：四区保留来源证据，但默认主视图不展示全部聊天噪声。群友消息可查询，仅在熬鹰回复所需时引用上下文；群友自述仓位不纳入熬鹰持仓。
1. 交易信号推送：最高处理优先级。校验目标 topic + bot sender_id，动作与快照分开存储/展示；动作去重后进入高优先级提醒，快照更新仓位和新鲜度，不按每次浮盈变动重复提醒。解析失败仍保留原文并提示未识别，禁止静默丢弃。机器人内容只可称「群机器人报告」，不能称交易所已核验实盘。
2. 禁言群：完整收录、主视图突出展示。本人观点和风险信息保留上下文；连续短句可组合成一组通知但逐条原文与编辑历史保留。初期标注本人发言，不用不可靠自动分类压掉消息。
3. 聊天群：与禁言群同属重点观点来源。优先提取熬鹰本人发言、相关图片和被回复内容；普通群友消息不触发熬鹰动态提醒。本人闲聊与市场观点需可区分，先保证不漏本人发言，再按实际样本评估摘要规则。
4. 消息通知：保留和分类查询，默认静默；不占据核心交易动态视图，不因助理或群友提到币种就生成交易信号。
按聊天重要性调整展示和通知，不降低交易、禁言、本人发言的实时采集可靠性。历史回补、重连补洞不得当成新交易轰炸通知。具体端侧推送随 I3b 实现，本阶段仅定义路由，不虚报通知已上线。
