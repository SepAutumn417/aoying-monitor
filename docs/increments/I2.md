# I2 · Telegram 采集与时间线

状态：**待验收**（I2.1 收口）
日期：2026-11-05 ~ 2026-11-07
版本：后端 0.3.0 · Web 0.3.0

## 本增量解决什么

I1 之后系统能登录、能收推送，但页面里全是示例数据。I2 把第一个真实来源接进来：用 Telethon 用户会话只读监听取熬鹰的 Telegram 发言，把消息原文、媒体、编辑历史、删除状态落库，并通过已有的 WebSocket 链路在几秒内推到 Web 与手机。

到这一步为止，系统里唯一的真实数据就是 Telegram；持仓、提醒、其它四个来源仍是示例或占位。

## 做了什么

| 端 | 内容 |
| --- | --- |
| 后端 | 采集器（Telethon 用户会话、惰性导入）；账号/会话/消息/编辑历史 4 张表；`/api/telegram/*` 9 个端点；首个群回补最近 200 条，之后 `min_id` 增量；每 5 分钟自动补洞；编辑归档旧文本、删除打时间戳不删行；媒体落盘 |
| Web | 「数据源」页：启停采集、发现会话、关注/取消关注、手动补拉；「发言」页改为真实消息流，支持会话/类型（全部·含媒体·已编辑·已删除）/时间范围（今日·近 7 天·全部）筛选与关键词搜索；被编辑的消息可展开看历史版本 |
| 部署 | 镜像补装 telethon；compose 给 api 挂 `./data` 卷（会话文件与媒体必须活过重启）；`.env.example` 的 Telegram 段与代码对齐 |

## 数据表

| 表 | 说明 |
| --- | --- |
| `telegram_accounts` | 一个 Telegram 用户账号（label/phone/session_path/连接状态与错误） |
| `telegram_dialogs` | 关注范围（chat_id/title/kind/enabled/last_message_id/last_synced_at），`(account_id, chat_id)` 唯一 |
| `telegram_messages` | 消息当前态（原文/发送者/媒体/`edited_at`/`deleted_at`），`(dialog_id, message_id)` 唯一 |
| `telegram_message_revisions` | 每次编辑被替换掉的旧文本，`(dialog_id, message_id, replaced_at)` 唯一使重复投递幂等 |

删除不删行，只写 `deleted_at`：时间线里要能解释「这里原本有条消息，后来被删了」。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/telegram/status` | 采集器状态 + 账号 + 会话数 + 已存消息数 |
| POST | `/api/telegram/start` / `stop` | 启动 / 停止采集 |
| GET | `/api/telegram/dialogs` | 已收录会话列表（含每条会话的消息数） |
| GET | `/api/telegram/discover` | 直接问 Telegram 要会话列表，供勾选（采集器未运行返回 409） |
| POST | `/api/telegram/dialogs/{chat_id}/follow` | 关注；运行中会重建事件过滤器，**无需重启** |
| DELETE | `/api/telegram/dialogs/{chat_id}/follow` | 取消关注 |
| GET | `/api/telegram/messages` | 时间线数据。参数：`limit` `before_id` `chat_id` `include_deleted` `include_revisions` `kind=media\|edited\|deleted` `since`（ISO 时间） |
| POST | `/api/telegram/sync` | 手动补洞。改为后台任务，立即返回；同一时刻只跑一遍 |

新增事件：`telegram.message` / `telegram.message.edited` / `telegram.message.deleted`，经 `/ws` 推到手机与浏览器。

## 怎么自己验证

### 1. 后端测试（本机一条命令）

```bash
cd backend
python -m pytest
```

首次需要装依赖。本机 pip 无法使用（见「已知限制」），用仓库脚本从 PyPI 直接取 wheel：

```bash
python scripts/fetch_deps.py "sqlalchemy==2.0.44"
```

期望：**27 passed**（I1 的 12 个 + I2 的 15 个）。

### 2. 让采集器真正连上 Telegram

前提：`TG_API_ID` / `TG_API_HASH` 已填，且 4 个群已用该账号加入。

```bash
cd backend
python -m app.telegram_login    # 一次性登录，写出 data/telegram.session
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

打开 Web → 「数据源」→ 启动 → 发现会话 → 勾选要跟的群。首次关注会补最近 200 条。

### 3. 验收动作（对应计划里的三条）

1. 在群里发一条消息 → Web「发言」页 10 秒内出现。
2. 在 Telegram 里编辑那条消息 → 页面上出现「已编辑」徽标，点「查看历史版本」能看到编辑前与当前两版。
3. 断网 5 分钟再恢复 → 不丢消息（`catch_up` + 每 5 分钟 `min_id` 补洞；也可手动点「补拉」）。

### 4. Web

```bash
cd web
npx tsc --noEmit
npm test
npm run build
```

## 已知限制与规格偏差

1. **采集器在 API 进程内**（规格写的是独立 `worker` 进程 + Postgres `LISTEN/NOTIFY`）。当前单用户、单容器、QPS 极低，拆进程只增加部署复杂度；事件总线与部署方式留到 I7 一并切换，接口不变。相应地 `api` 只允许跑 1 个 worker。
2. **调度用自建 asyncio 循环**，没有引入 APScheduler（规格 §5 提到）。本机 pip 不可用，且 APScheduler 4.x 的 API 与 3.x 差异大；两个定时任务（补洞、日汇总）用 `asyncio.Task` 足够。I3 需要更多定时任务时再评估。
3. **表名保留 `telegram_*`**，没有改成规格里的 `raw_messages`。改名只有空迁移成本，没有收益；规格已同步记录该偏差。
4. **密码仍是 bcrypt(rounds=12)、访问令牌 30 分钟**（规格写 Argon2id / 15 分钟）。单用户只读系统，bcrypt 足够；换 Argon2 要同时改 Android 登录逻辑，放 I7。
5. **Web 令牌存 localStorage**（规格要求 HttpOnly Cookie）。改它要同时动 Web 与 Android 两套会话逻辑，放 I7。
6. **币种筛选未做**：消息里还没有「币种」这个字段，硬做只能正则猜，属于假功能。等 I3a 有了符号抽取再按真实结构化字段筛。
7. **媒体只落盘不提供下载接口**：文件名与大小入库，Web 暂不展示图片。
8. **历史版本只存文本**：编辑前如果带媒体，只记录 `media_kind`，不保留旧媒体文件。
9. **本机环境限制**（不影响服务器）：`backend/.vendor` 里有若干条目被 Windows ACL 锁死，`pip` 因临时目录同样问题不可用，`vite`/`vitest` 因沙箱禁止 `spawn` 无法运行。`conftest.py` 会在插入 `sys.path` 前探测可读性，并用 `.pylib` + `.pytest-tmp` 绕开。
10. **`sqlalchemy` 钉在 `<2.1`**：2.1.x 在本机可以让整个测试套件挂死（单文件却正常），2.0.44 全套通过。等上游修复后再放开。
