# Roadmap: 熬鹰资本监控系统 v1.0

2026-10-30。供主代理整理正式需求映射与用户审批，尚未批准执行。标准粒度，6个阶段。

## 基线与范围

现有仅有SQLite事件日志原型与2项测试；没有认证/WSS服务、安卓App或业务采集。已有HTTPS设施不是产品闭环，Gotify实验不计入App验收。
核心价值是用户在大陆不连VPN，及时获知熬鹰资本真实仓位变化，并能查看观点、原文与历史。无自动交易、无Gotify依赖、不承诺保活必达。
正式需求见REQUIREMENTS.md，17条v1需求映射至6阶段。本文为待用户确认的路线图；不构成阶段执行批准。

## Phases

- [ ] **Phase 1: 自有手机接收与响铃闭环** — 用合成事件证明K50后台接收、恢复与提醒可用。
- [ ] **Phase 2: Telegram真实仓位与发言监控** — 四话题接入，识别同条消息编辑产生的真实仓位操作。
- [ ] **Phase 3: App中的完整监控视图** — 用户在手机查看当前仓位、动态、变化与投递状态。
- [ ] **Phase 4: X发言与跨平台身份关联** — 本人公开发言进入统一时间线，并可追溯来源。
- [ ] **Phase 5: Fomo与OKX交易动态** — 按实际权限接入可见订单/仓位变化，明确数据边界。
- [ ] **Phase 6: 稳定性与隐私验收** — 长时运行、备份恢复、故障观察与隐私边界。AI作为v2后续里程碑。

## Phase Details

### Phase 1: 自有手机接收与响铃闭环
**Requirements**: [AUTH-01, DATA-01, ACK-01, APP-01, ALERT-01, OPS-01]
**Goal**: 用户在K50上不连VPN，能及时收到自有服务器的测试事件、听到提醒并手动停止；断连后能补齐且不重复提醒。
**Depends on**: Nothing。沿用事件日志原型但补齐并发、认证与回执，不将原型视为已交付。
**需求簇**: 设备配对/撤销、HTTPS/WSS、持久化队列/游标、设备收到与人工已知晓分离、后台服务、声音振动与停止、连接状态、备份/恢复及故障可见。
**Success Criteria**:
1. 用户安装自有App并配对，在Wi-Fi和移动网络、VPN关闭时收到合成事件，看到连接及权限状态；撤销设备后旧连接不能继续读取。
2. 锁屏及至少两小时待机可听到测试提醒并停止，振动和音量表现有实机证据；被强行停止/关机的边界明确显示，不能承诺继续收信。
3. 切网、断网、App与服务正常重启后按游标补收；重复事件不重复响铃，过期事件显示延迟且不作为实时操作提醒。
4. 服务端可区分排队、发出、手机已保存与用户已知晓；非法设备与跨设备读取被拒绝，敏感令牌不出现在URL或日志。
5. 按P1-VALIDATION至少24小时/100条建议矩阵验收，正常在线目标100%到达、P95≤5秒，阈值执行前锁定；不通过先解决该链路，不推进业务扩建。
6. 合法适用的Android14前台服务类型、Doze网络和后台声音有明确真机结论；任一关键能力未通过则暂停平台扩建。
本阶段24小时/100条为合成事件可行性关卡；Phase6须在真实来源接入后另做完整回归，不能沿用此证据勾选E2E-01。
**Plans**: TBD，建议3个纵向计划：认证测试事件闭环、后台提醒与恢复、服务器部署及真机验收。
**UI hint**: yes
**未知输入**: Android14/OS2.0.10.0.ULNCNXM已确认；响铃上限、多事件会话及锁屏摘要默认值需阶段方案确认；Android前台服务类型与分发方式必须先研究，不伪装成电话/闹钟绕限制。

### Phase 2: Telegram真实仓位与发言监控
**Requirements**: [TG-01, TG-02, TG-03]
**Goal**: 用户能及时收到熬鹰本人及指定助理的信息，仓位提醒对应实际操作而非动态文本刷新。
**Depends on**: Phase 1
**需求簇**: 独立TG授权、四话题稳定ID/本人身份、原始及编辑版本保存、编辑监听与周期核对、仓位快照/差异、幂等事件投递、采集健康与恢复。
**Success Criteria**:
1. 四话题分别可收到正确来源内容；聊天群重点本人，助理名单明确，不把同名成员认成本人。
2. 同条动态消息的新开仓/加仓/减仓/平仓分别产生独立变化通知；价格、浮盈、时间刷新仅更新展示，无重复操作提醒。
3. 每条变化都可回看前后快照及原始编辑依据；未知单位/缺失字段标记未知，不把不完整快照推断成平仓。
4. 漏编辑、采集断线及进程重启通过核对/补收发现缺口；同事件正常重放不重复提醒，故障状态可见。
5. 接入真实原文前落实受限存储、备份权限与锁屏摘要策略，不等Phase6才处理。

### Phase 3: App中的完整监控视图
**Requirements**: [UI-01, UI-02]
**Goal**: 用户能在一个App内理解当前仓位及其来龙去脉，不必把通知列表当作唯一记录。
**Depends on**: Phase 2
**需求簇**: 当前仓位、时间线、变化记录、原文/编辑详情、来源筛选、连接/投递状态、提醒配置、隐私与数据保留管理。
**Success Criteria**:
1. 仓位页展示最近有效快照与源时间；过期、无数据和读取失败分别显示，不能把错误显示为空仓。
2. 用户能按来源和时间查看观点、动态及仓位变化，点入详情查看原文和前后差异。
3. 用户能查看设备接收与已知晓状态、配置声音/振动/锁屏显示，停止响铃不被误标为已交易。
4. 离线可查看已保存记录；恢复后补齐；保留与备份策略及删除操作的实际范围明确。

### Phase 4: X发言与跨平台身份关联
**Requirements**: [X-01]
**Goal**: 熬鹰的X公开发言进入同一App，用户能确认来源与时间，不因采集重复收到同一发言。
**Depends on**: Phase 3
**需求簇**: X入口及合法访问方式、本人身份映射、源内去重、统一时间线、抓取延迟及错误可见。
**Success Criteria**:
1. 已核实账号的新帖在已声明的检测时效内出现，原文与链接可追溯；回复/引用/转推的纳入范围明确。
2. 分页、回填、重试不生成重复通知；接口限频/无权限可见，不能冒充实时或完整监控。
3. 相同信息跨平台先关联显示，不在证据不足时误合并两笔不同操作。

### Phase 5: Fomo与OKX交易动态
**Requirements**: [FOMO-01, OKX-01]
**Goal**: 用户在同一App看到这两个平台实际允许获取的熬鹰交易/仓位变化及清楚的数据边界。
**Depends on**: Phase 4（数据模型复用Phase 2，若X外部入口阻塞可由用户批准调整顺序）
**需求簇**: 分别核实平台与公开身份、接口/链上数据资格、归一化仓位、延迟/缺口、跨来源关联与追溯。
**Success Criteria**:
1. 每个平台有真实账号/地址与可见字段清单；用户可区分“不可获取”和“无仓位”，不承诺读取私有订单。
2. 经真实样本核对的变化生成提醒并保留来源、单位和时间；断线、分页及限频恢复不漏已可获取事件。
3. 用户能按平台查看仓位与操作；跨平台重复信息有依据才关联，来源冲突保留并显示。
4. 每平台单独验收或由用户明确变更范围；一个平台不可获取不掩盖另一平台状态。
**Plans**: TBD，Fomo与OKX分别验证，不共享未经核实的能力假设。
**UI hint**: yes
**未知输入**: Fomo具体网址及账号/链上地址、OKX公开主页/跟单入口、接口权限、预算与可接受检测延迟。

### Phase 6: 稳定性与隐私验收
**Goal**: 现有监控与App在明确边界内长期运行，故障可见、数据可恢复且隐私措施有证据。
**Depends on**: Phase 5；外部平台阻塞时须用户明确调整范围，不以不可获取代替已交付。
**Requirements**: [OPS-02, PRIV-01, E2E-01]
**Success Criteria**:
1. 按约定保留期执行容量管理、备份与恢复，来源/设备断线可查；独立探活能发现整机失联。
2. 设备撤销、锁屏隐私、日志/密钥/备份边界复核通过；基础认证/TLS从Phase1开始，不能拖到本阶段。
3. K50至少24小时100条测试报告分场景给出送达、延迟、声音与离线补收；明确强停/关机边界，不承诺必达。
